The problem

Every project is built on packages written by other people. Those packages keep releasing new versions, and somebody has to decide whether to move up.

?

Nobody really knows what will break

A version number does not tell you if your code still works. Teams find out after they merge.

!

Old versions have known holes

Staying on an old version keeps reported security problems in your project.

§

Licences change quietly

An upgrade can drag in a package your company is not allowed to ship.

⋮

Existing tools only read labels

They read package files and guess. They never actually build the project and run it.

So the honest answer today is normally "let us merge it and hope".

How we solve it

Do not guess. Actually do the upgrade twice and compare what really happened.

Environment A

Today's versions

Build the project clean, install exactly what it uses now, run its own tests, write everything down.

compare
Environment B

The proposed version

Build a second clean copy with the one package changed, run the same tests, write everything down.

Anything that is different between A and B was caused by the upgrade. That difference is our evidence.

Our answer is always one of three
Accept Reject Insufficient Evidence

Where this helps

Anywhere somebody has to approve a dependency change and wants a reason, not a feeling.

Software teams

Upgrade on purpose instead of avoiding it for months because it feels risky.

Security work

Patch a reported hole and prove in the same run that nothing else broke.

Companies with licence rules

Write the rule once and have every upgrade checked against it automatically.

Open source maintainers

Attach real evidence to an upgrade request instead of asking reviewers to trust it.

Students and small projects

Learn what an upgrade actually does, because every step is written down.

Audits

Keep a downloadable record of why each upgrade was allowed or refused.

Our scope and plan

We will do

  • Python projects, one packaging style
  • One direct upgrade per run
  • Clean builds, real test runs
  • Conflicts, security and licence rules
  • Website, terminal tool and pipeline step
  • A benchmark of 20 to 25 real projects

We will not do

  • Fix the broken code for you
  • Other languages
  • Every packaging tool that exists
  • Let a language model decide the answer

Conclusion

An upgrade decision should come with proof.

  • We build the project twice and run its own tests both times.
  • Every Accept or Reject points at a build log, a test result or a policy rule.
  • No language model decides anything; the evidence decides.
  • It already works end to end on our two demo cases.
